## 业务背景

AI 创作者社区冷启动阶段，运营者每周被困在三件事里：

1. **周复盘耗时**：7 张飞书表手动汇总数据、翻访谈记录写画像，每次 2 小时以上
2. **话术凭感觉**：邀约话术无法复用经验，效果好坏全靠个人手感
3. **课件搜不到**：40 天课程的 528 张课件是图片格式，重复答疑占社群问题 60%

平台本身也有定位问题——Skill 商店被埋没在二级页面，80% 用户不知道它的存在；Top 创作者两周后不再上传。

## 用户调研

通过 24 份问卷 + 访谈，推翻了四个初始假设：

| 我们假设 | 调研发现 | 转向 |
|----------|----------|------|
| 用户需要系统课程 | 67% 反馈「太笼统」，点击率 <5% | 场景化即用方案 |
| Skill 商店是附加功能 | 80% 不知道有 Skill 库 | 提至首页核心位 |
| 发课就是运营 | 重复问题占答疑 60% | OCR + RAG 问答机器人 |
| 创作者靠热情留存 | Top 创作者 2 周后不再上传 | 身份认证 + 成长体系 |

关键数据：直接问需求的邀约回复率 66%，泛泛「学习搭子」互动率仅 3%。

## 人机方案

| 环节 | AI/系统负责 | 人负责 |
|------|------------|--------|
| 周复盘 | 自动汇总数据 + 访谈，生成 9 段式群体画像 | 确认画像、制定运营策略 |
| 话术生成 | 画像驱动生成 3 条不同风格话术，自动写回飞书 | 审核后发送 |
| 课件问答 | RAG 检索 528 张课件，带出处回答 | 超纲问题转人工 |
| AI 日报 | 自动搜集新闻 + AI 主编筛选 + 漫画生成 + 排版推送 | 确认每日内容质量 |
| 任务执行 | 飞书工作台自动分配任务、汇总状态 | 完成任务、一键勾选 |

关键设计：话术生成器死锁 JSON 输出，因为要自动写回飞书不同字段；超纲问题拒答而非编造。

## 子项目一：AI 运营平台

把运营者每周「汇总数据 → 翻访谈 → 写画像 → 写话术 → 录入文案库」的 2 小时手动流程，重构为 Dify 上一键运行的自动化闭环。

| 应用 | 类型 | 做什么 | 关键设计 |
|------|------|--------|----------|
| 周画像生成器 | Workflow | 投放数据 + 访谈 → 9 段式群体画像报告 | 每个痛点附访谈原话作证据 |
| 话术生成器 | Workflow | 画像驱动生成 3 条不同风格话术 | JSON 输出，Code 解析后自动写回飞书 |
| 主控 Workflow | Workflow | 8 节点 HTTP 串联画像 → 话术全链路 | Code 节点 json.dumps 解决转义 |

> 问答助手（RAG 问答）见下方[子项目二](#子项目二rag-问答机器人dify--公众号落地)，它从 Dify 搭建演进到微信公众号落地。

**效果**：周复盘从 2 小时压缩到 3 分钟；话术自动写回飞书文案库。

## 子项目二：RAG 问答机器人（Dify → 公众号落地）

同一个问答机器人的两个阶段：先在 Dify 上搭建验证，再落地接入微信公众号，知识库从 16 篇文档扩展到 528 张课件 OCR。

### 阶段一：Dify 搭建（问答助手）

在 Dify 上用 Chatflow 搭建 RAG 问答助手，验证社群问答场景：

- RAG 检索 16 篇运营文档，带出处回答社群问题
- TopK=3，相似度阈值 0.5，超纲问题拒答而非编造
- 20 题黄金集评测（学习路径 / 工具推荐 / 社群活动 / 话术查询），通过率 90%（18/20）

### 阶段二：微信公众号落地（课件问答机器人）

验证可行后，将 40 天课程的 528 张课件 OCR 化，落地接入微信公众号，让学员直接在公众号提问：

- 学员在公众号提问，RAG 检索课件内容后带出处回答，超纲转人工
- 15 题评测（引用准确 / 边界拒答 / 口语化召回），最终 100% 通过
- 检索匹配率从最初的 5/15 提升到 15/15——**不是换了更大的模型**，而是写脚本逐条分析失败 case，定位到「长句 AND 匹配过严 + 口语化表达（3k/2米5）与课件书面语不匹配」，调整分块策略和同义词映射后解决

### 演进对比

| 维度 | 阶段一（Dify） | 阶段二（公众号落地） |
|------|---------------|---------------------|
| 知识库 | 16 篇运营文档 | 528 张课件 OCR |
| 接入方式 | Dify Chatflow 内嵌 | 微信公众号 API |
| 用户 | 运营者内部 | 学员（外部用户） |
| 评测集 | 20 题（运营场景） | 15 题（课件场景） |
| 通过率 | 90%（18/20） | 100%（15/15） |
| 匹配率 | — | 5/15 → 15/15（优化分块策略） |

## 子项目四：AI 日报工作流

> 代码见 [`ai-daily-workflow/`](./ai-daily-workflow) 目录

每日自动搜集 AI 新闻 → AI 主编筛选解读 → 生成《经济学人》风格编辑漫画 → 复古报纸三栏排版 → 微信个人 Bot 推送。

### 架构

**Dify 云版工作流（8 节点）**：定时触发 → Google 搜索 → AI 新闻主编（deepseek-chat，按影响力/稀缺性/趋势/传播评分筛选）→ 解析 JSON → 漫画导演（生成英文图片 prompt，The Economist 风格）→ 通义千问生图（1280×720）→ 整理输出 → 结束

**微信 Bot（Python）**：wechat-ilink-bot 框架，关键词触发 + 每天 8:00 定时推送，HTML/CSS + Playwright 渲染复古报纸排版 PNG

### 效果

- 每天自动产出 1 份带编辑漫画的 AI 日报，零人工干预
- 报纸排版：报头 + 横向通栏漫画 + 三栏（讯息/总结影响/行业意义）
- 复古纸张纹理背景，《经济学人》编辑漫画风格

### 文件清单

| 文件 | 说明 |
|------|------|
| `ai_news_bot.py` | Bot 主程序（Dify 调用 + 排版 + 微信收发） |
| `newspaper_render.py` | HTML/CSS 报纸排版 + Playwright 截图 |
| `wechat_login.py` | 扫码登录获取 token |

## 平台重设计与成长体系

基于调研结果，对平台进行重设计：

| 页面 | 改版前 | 改版后 |
|------|--------|--------|
| 首页 | 信息流图文笔记 | Skill 库推荐 + 场景入口 |
| 工具箱 | 二级页面附加功能 | 一级导航，分类展示 |
| 个人主页 | 只有作品列表 | 身份等级 + 成长值 + 成就徽章 |

**成长体系**：三类身份（学习者 / 创作者 / 导师）× 五级等级（Lv1 探索者 → Lv5 导师），成长值奖励「有用」（下载 +5、Fork +10）而非「认同」（点赞权重低），含防刷分机制。

|--------|------|------|--------|

## 失败案例与迭代

### 失败案例 1：RAG 检索匹配率仅 5/15

- **现象**：课件问答机器人初版，15 题评测只通过 5 题，大量问题检索不到相关课件
- **第一反应**：换更大的模型、增加 TopK 数量——但效果提升有限
- **根因定位**：写脚本逐条分析失败 case，发现是分块策略问题——长句被 AND 匹配过严，口语化表达（「3k」「2米5」）和课件书面语对不上
- **解决方案**：调整分块策略（按语义段落而非固定长度），增加同义词映射
- **结果**：匹配率从 5/15 → 15/15，**没有换模型，只改了分块**

### 失败案例 2：Dify HTTP 节点返回 400

- **现象**：主控 Workflow 串联话术生成器时，HTTP 节点频繁返回 400 错误
- **排查**：对比手动调用成功的请求和 Dify 模板替换后的请求，发现 body 中的 JSON 含换行符时，模板替换会破坏 JSON 结构
- **解决方案**：在 HTTP 节点前加 Code 节点，用 Python `json.dumps()` 预序列化 body，确保转义正确
- **结果**：400 错误彻底消失，全链路稳定运行

### 失败案例 3：AI 日报 V1 四宫格漫画信息分散

- **现象**：V1 版本用四宫格漫画展示每日新闻，用户反馈「看不懂四张图之间的关系」「信息量太散」
- **根因**：四宫格各自独立，没有统一的视觉叙事线；漫画风格不统一，有的写实有的卡通
- **迭代方向（V2）**：
  - 放弃四宫格，改为**单张横向编辑漫画**（The Economist / NYT 风格），用一个画面讲一个核心故事
  - 新增「漫画导演」LLM 节点，专门负责把新闻要点转化为统一风格的图片 prompt
  - 排版改为复古报纸三栏布局，漫画作为通栏主视觉
- **结果**：V2 版本视觉叙事更集中，用户理解成本降低

### 迭代对比总览

| 维度 | V1 | V2 | 改进点 |
|------|----|----|--------|
| 课件 RAG 匹配率 | 5/15 (33%) | 15/15 (100%) | 分块策略优化，非换模型 |
| 周复盘耗时 | 120 分钟 | 3 分钟 | Dify 自动化全链路 |
| 话术生成 | 手动写，凭感觉 | 画像驱动 3 条，自动写回飞书 | JSON 死锁输出 + Code 节点 |
| AI 日报漫画 | 四宫格，风格混乱 | 单张横向编辑漫画，统一风格 | 新增漫画导演节点 |
| 实习生填表 | 30 分钟/天，5 步 | 5 分钟/天，3 步 | 飞书 Base App 工作台 |

## 关键产品决策

不是选「最先进的技术」，而是选「最适合这个场景的方案」：

| 决策点 | 选择 | 为什么不选另一个 |
|--------|------|------------------|
| 知识方案 | RAG | Fine-tuning 每周重新训练成本高，且无法引用来源 |
| 应用架构 | Chatflow + Workflow 拆分 | 一个应用会让交互逻辑混乱，且 Workflow 可被 HTTP 串联 |
| 输出格式 | JSON 死锁 | 自由文本无法可靠解析写回飞书字段 |
| 日报漫画 | 单张横向编辑漫画 | 四宫格信息分散，用户理解成本高 |
| 成长值激励 | 奖励「有用」（下载/Fork） | 奖励「认同」（点赞）容易刷分，且不反映真实价值 |

## 项目反思

这段经历走完了「发现问题 → 定义方案 → 落地工具 → 验证效果」的完整闭环。24 份问卷推翻了「发课程 = 提供价值」的假设；检索匹配率从 5/15 到 15/15 不是换了更大的模型，而是写脚本定位到「长句 AND 匹配过严」这个具体原因。

AI 产品经理的价值不在于调 API，而在于定义「什么是好」——有出处、不编造、周复盘从 2 小时变 3 分钟——然后用数据验证它。
